# SF 탐사단 홈페이지 통합 운영계획

> 문서 책임자: 보라(운영 총괄)
> 적용 대상: `https://www.sf-explorer.net` 및 연결된 Admin·Notion·Supabase·GitHub Actions·Vercel 자동화
> 버전: 1.0 초안
> 기준일: 2026-08-08
> 상위 기준 문서: [`product-roadmap.md`](./product-roadmap.md)

## 0. 목적과 운영 판정

SF 탐사단은 많은 글을 빠르게 생산하는 포털이 아니라 `발견 → 기록 → 연결`을 안정적으로 유지하는 **조용한 SF 관측소**다. 운영의 우선순위는 다음 순서로 둔다.

1. 공개 정보의 정확성과 출처
2. 사용자 기록의 개인정보·공개 범위
3. 오래 유지할 수 있는 작은 운영량
4. 최신성
5. 트래픽과 게시물 수

게시물 수를 늘리기 위해 출처 확인, 권리 확인, 사용자 승인, Production 검증을 생략하지 않는다. 운영 성공은 “많이 등록함”이 아니라 “잘못 공개된 정보가 없고, 새 정보가 예측 가능한 일정으로 보강되며, 문제가 생겼을 때 추적·수정할 수 있음”으로 판정한다.

## 1. 운영 범위와 원천 시스템

| 공개 영역 | 내용 | 원천 시스템 | 기본 공개 방식 | 운영 책임 |
|---|---|---|---|---|
| 작품·개념 아카이브 | SF 작품 및 개념 정보 | Notion → 영속 스냅샷 → 웹 | 공개 상태 자료만 동기화 | 보라·선영 |
| 새로 포착된 SF | 신작, 공개 예정, 편집 추천 | Supabase `sf_discoveries` + Admin | 초안·검수·최종 발행 분리 | 보라, 사용자 최종 승인 |
| 미디어 아카이브 | SF 관련 미디어, SF 고전 영화 | Notion 미디어 DB → 영속 스냅샷 → 웹 | 제한된 자동등록 예외 + 사후 감사 | 윤경·보라 |
| 탐사 로그 | 개인 감상과 공개 신호 | Supabase 계정 기록, 일부 Notion 공개 로그 | 사용자가 공개 범위를 직접 선택 | 사용자·보라 |
| 커뮤니티 | 자유글, 작품추천, 질문, 토론, 댓글 | Supabase | 로그인 사용자의 즉시 공개 + 사후 관리 | 게시자·보라 |
| 홈페이지 | 위 공개 자료의 요약 진입점 | `/api/home-feed` 통합 스냅샷 | 실제 자료만 제한 노출 | 보라·리아 |

### 원천 관리 원칙

- 같은 공개 필드를 Notion과 Supabase 양쪽에서 동시에 수정하지 않는다.
- URL·ISBN13·외부 상품 ID 등 정규 식별자를 중복 판정의 우선 기준으로 사용한다.
- 설명, 출처, 이미지 권리 메모, 공개 상태를 한 필드에 섞지 않는다.
- 공개 화면은 승인된 공개 투영만 읽고 내부 메모·승인 기록·사용자 식별자를 반환하지 않는다.
- Notion은 미디어·기존 아카이브의 편집 원천, Supabase Admin은 신작·공개 예정·편집 추천의 발행 원천으로 유지한다.

## 2. 세 가지 운영 레인

### A. 제한적 자동등록 레인 — 미디어 아카이브

적용 범위는 `SF 관련 미디어`의 검증된 한국어 영상·기사로 제한한다. `SF 고전 영화`는 자동수집하지 않고 수동 등록한다.

`후보 탐색 → SF 적합성 검사 → 원문 접근 확인 → URL 중복 검사 → 메타데이터 정규화 → Notion 즉시 등록 → 신규 건이 있을 때만 캐시 갱신 → 다음 운영일 감사`

자동등록 조건:

- 한국어 자료 또는 한국 SF 맥락이 명확하다.
- 원문 URL이 실제로 열리고 제목·게시자·공개일을 확인할 수 있다.
- 기존 URL과 중복되지 않는다.
- 분류는 `SF 관련 미디어` 또는 `SF 고전 영화` 중 하나다.
- 설명은 URL·홍보 문구 없이 80~160자 한국어 요약이다. 요약이 어려운 뉴스는 정리된 본문 앞부분을 같은 범위로 사용한다.
- 기사에는 접근 가능한 `og:image`/`twitter:image` 대표 이미지가 있고, 영상에는 유효한 썸네일이 있다.
- 개인 연락처, 유료 본문 복제, 확인되지 않은 주장, 불법 업로드 정황이 없다.

자동등록 후 다음 운영일에 윤경이 신규 항목 전체 또는 10건 초과 시 최소 10건과 고위험 항목 전부를 감사한다. 부적합 항목은 즉시 보관하고 사유를 기록한다.

### B. 승인형 편집 레인 — 신작·공개 예정·편집 추천

`BRIEF → RESEARCHING → SELECTION_REVIEW → SELECTION_APPROVED → DRAFTING → REVIEW_READY → APPROVED → 사용자 최종 발행 → PUBLISHED`

- 자동화는 `DRAFT` 생성과 provenance 보강까지만 수행한다.
- `PUBLISHED`, `published_at`, 승인 상태는 자동화가 설정하지 않는다.
- 침묵, 응답 지연, 일정 만료를 승인으로 간주하지 않는다.
- 편집 추천은 선정 승인과 원고 승인을 별도 기록한다.
- 발행 직전 Preview에서 모바일·데스크톱·출처·표지·alt text를 확인한다.
- 사용자가 마지막 발행을 승인하고 Admin의 최종 발행 동작을 수행한다.

### C. 사용자 게시 레인 — 탐사 로그·커뮤니티·댓글

`사용자 작성 → 입력 검증 → 즉시 공개 또는 비공개 저장 → 사후 신고/운영 검토 → 유지/숨김/보관/삭제`

- 탐사 로그의 공개 범위는 `PRIVATE_ARCHIVE / ANON_NETWORK / PUBLIC_SIGNAL`을 사용자가 직접 선택한다.
- 커뮤니티 게시물과 댓글은 로그인 사용자만 작성한다.
- 사용자 이름은 인증 정보에서 파생하고 임의의 타인 이름을 서버에 제출하지 못하게 한다.
- 첨부는 HTTP(S) URL만 허용하며 파일 업로드는 별도 권리·악성코드 검토 체계가 생기기 전까지 도입하지 않는다.
- 신고·숨김 UI와 운영 처리 이력이 완성되기 전에는 커뮤니티 확장을 P1으로 보류한다.

## 3. 역할과 승인 권한

| 역할 | 상시 책임 | 승인 권한 | 부재 시 |
|---|---|---|---|
| 사용자(사이트 소유자) | 운영 목적·공개 범위·Production 최종 결정 | 편집 추천 최종 발행, Production 승격, 중요한 삭제·정책 변경 | 승인을 기다리며 자동 진행 금지 |
| 보라 | 운영 총괄, 우선순위, 콘텐츠 캘린더, 최종 검수, 장애 판정 | 일반 콘텐츠 승인, 출시 후보 판정 | 윤경이 안전 조치만 수행하고 공개는 보류 |
| 윤경 | 원출처, 날짜, 서지, 중복, 권리·개인정보, 자동등록 감사 | 출처 검증 통과/반려, 긴급 숨김 권고 | 보라가 검토하되 고위험 공개는 보류 |
| 선영 | SF 한국어 문체, 요약, 제목, spoiler·맥락 편집 | 문체·구성 검수 | 보라가 최소 수정 후 다음 회차 재검수 |
| 현정 | 정보 위계, 이미지, alt text, 접근성, 모바일 경험 | 디자인 검수 통과/반려 | P1 이상 UI 변경은 출시 보류 |
| 리아 | 코드·테스트·캐시·배포·복구·관측성 | 기술 gate 통과/반려 | 코드·Production 변경 보류 |

### RACI 요약

- 신작/공개 예정: 윤경 검증, 선영 편집, 보라 승인, 사용자 발행.
- 편집 추천: 윤경 조사, 선영 원고, 현정 시각 검수, 리아 Preview, 보라 최종 판정, 사용자 발행.
- 자동 미디어: 자동화 등록, 윤경 다음 운영일 감사, 보라 예외 판정, 리아 장애 처리.
- 커뮤니티: 사용자가 작성 책임, 보라 운영 판정, 윤경 개인정보·법적 위험 검토, 리아 숨김/복구 지원.
- Production: 리아 후보 준비, 윤경·현정 독립 검토, 보라 판정, 사용자 명시 승인.

## 4. 콘텐츠별 등록·수정·보관 기준

### 4.1 신작·공개 예정

필수 필드:

- 제목, 작품 형식, 출시일 또는 공개 예정 범위
- 저자·창작자, 출판사·제작사
- ISBN13 또는 공식 식별자(해당 시)
- 대표 출처명과 HTTPS URL
- 500자 이내 요약
- 이미지 원본 URL, alt text, 권리 상태
- 조사 시각과 내부 검수 메모

발행 조건:

- 국내판/공식 공개 여부를 원출처로 확인한다.
- 날짜가 불확실하면 단정하지 않고 `예정`으로 표시한다.
- 자동수집 자료의 표지 권리가 `UNVERIFIED`면 발행하지 않는다.
- 동일 작품의 판본·재출간·영상화를 구분한다.

### 4.2 편집 추천

- 한 기획은 명확한 독자·계절·질문을 가진다.
- 3권 추천은 6~9권 longlist 조사 후 선정한다.
- 국내 정식 한국어판 제목·저자·역자·출판사·ISBN13을 검증한다.
- 사실 주장마다 출처를 연결하고 인용은 판본·쪽수를 기록한다.
- 표지와 사진은 공식 홍보 자산, 허용된 API, 소유 자산을 우선한다.
- 공개 payload에서 내부 메모와 권리 검수 메모를 제거한다.

### 4.3 미디어 아카이브

분류는 다음 두 개만 사용한다.

- `SF 관련 미디어`: 작가 인터뷰, 강연, 출판/신간, 문학/비평, 과학·기술 SF 뉴스, 행사/공연
- `SF 고전 영화`: 연도 제한 없이 보존하는 고전 영화 자료

품질 계약:

- `설명`: 독자용 한국어 요약만 저장하며 URL·해시태그·구독 문구를 넣지 않는다.
- `URL`: 원본 canonical URL이며 중복 키로 사용한다.
- `이미지`: 기사 대표 이미지 URL. 접근 불가 시 기사 fallback을 사용한다.
- 영상은 원본 채널·공개일을 보존한다.
- `SF 고전 영화`는 일반 자료의 연도 정리 정책에서 제외한다.
- 삭제 대신 우선 보관하며, 중복·무관·원문 소실 사유를 내부 기록한다.

### 4.4 탐사 로그

- 개인 기록은 기본 비공개다.
- 공개 선택 전 제목·본문·메모·수치·태그를 Network에 노출하지 않는다.
- spoiler 상태를 목록·상세·접근성 이름까지 일관되게 적용한다.
- 계정 삭제 요청 시 비공개 기록 삭제, 공개 기록의 익명화/삭제 정책을 사용자에게 먼저 선택하게 한다.

### 4.5 커뮤니티와 댓글

허용:

- SF 작품 추천, 질문, 토론, 행사·강의 정보, 운영 제안

숨김 또는 삭제 검토:

- 개인정보·연락처 무단 공개
- 명백한 혐오·괴롭힘·위협
- 반복 광고·자동 생성 스팸
- 불법 복제 링크와 저작권 침해 신고
- 작품과 무관한 도배
- spoiler 미표시로 중대한 감상 피해가 예상되는 본문

처리 원칙:

- 긴급 개인정보·위협·불법 링크는 먼저 숨기고 24시간 내 판정한다.
- 일반 신고는 2영업일 내 확인한다.
- 단순 의견 차이는 삭제 근거가 아니다.
- 삭제보다 숨김/보관을 우선해 이력을 남기며, 작성자에게 사유와 이의 제기 경로를 제공한다.
- 운영자가 자신의 이해관계가 있는 글을 처리할 때는 윤경 또는 사용자에게 재검토를 요청한다.

### 4.6 외부 기고·제보

- 외부 기고와 제보는 미디어 자동수집과 분리된 비공개 접수 경로를 사용한다.
- 제출자, 연락 방법, 공개 동의 범위, 원고·이미지 권리, 철회 조건을 명시적으로 확인한다.
- 회원 전용·비공개 그룹·삭제된 개인 게시물은 검색 가능하더라도 자동수집하거나 재게시하지 않는다.
- 실명과 필명의 연결은 당사자가 공개한 근거와 동의가 없으면 노출하지 않는다.
- 향후 유료 원고를 도입할 때만 독점기간·원고료·2차 이용 조건을 별도 계약으로 정한다.

## 6. 콘텐츠 캘린더 원칙

### 기본 발행량

비용과 검수 품질을 우선해 다음을 상한이 아닌 안정적 기준으로 사용한다.

- 신작/공개 예정: 검증된 중요 항목 주 1~2건
- 편집 추천: 월 1건 이하

- SF 고전 영화: 월 1~2건
- 운영 공지: 정책·장애·중요 변경이 있을 때만

자동 미디어는 고정 수량 목표를 두지 않는다. 적합한 신규 원문이 없으면 0건이 정상이다.

- 작업 ID
- 콘텐츠 유형
- 한 문장 목적/독자
- 원천 시스템

- Production 승인자
- 발행 URL
- 정정/보관 상태
- 마지막 검토일과 다음 재검토일

캘린더는 새로운 CMS로 만들기보다 우선 기존 Admin과 연결되는 작은 운영표로 시작한다. 시스템 간 상태를 자동 양방향 동기화하지 않고 한 곳을 기준으로 삼는다.

## 8. 수정·정정·삭제 정책

### 사실 오류

정정 요청을 받을 공개 연락 경로와 담당자를 사이트에서 안내한다. 의견 차이와 검증 가능한 사실 오류를 구분하며, 이의가 해결되지 않으면 윤경 검토 후 사용자가 최종 판정한다.

1. 공개 화면에서 심각한 오정보인지 판정한다.
2. 원출처로 수정 내용을 검증한다.
3. 경미한 수정은 즉시 고치고 `updated_at`을 남긴다.
4. 의미가 바뀌는 수정은 내부 정정 기록에 이전 값·새 값·근거·수정자를 남긴다.
5. 잘못된 날짜·권리·개인정보가 포함되면 먼저 숨긴 뒤 수정한다.

### 링크 소실

- 원문이 이동했으면 공식 canonical URL로 교체한다.
- 원문이 삭제됐으면 대체 원출처를 찾되, 찾지 못하면 `원문 확인 불가`로 보관 검토한다.
- 링크가 사라졌다고 검색 결과·복제 사이트로 자동 교체하지 않는다.

### 보관과 삭제

- 운영 콘텐츠는 물리 삭제보다 `ARCHIVED` 또는 Notion 보관을 우선한다.
- 중복은 더 완전한 정본을 남기고 다른 항목을 보관한다.
- 개인정보·법적 요청은 공개를 즉시 중단한 뒤 사용자와 처리 범위를 결정한다.
- 사용자 게시물 삭제는 작성자 권리, 공개 댓글 관계, 법적 보존 필요성을 함께 검토한다.
- 대량 삭제 전 대상 목록과 예외를 출력하고 승인 후 실행한다.
- `SF 고전 영화`는 연도 기준 대량 정리에서 항상 제외한다.

## 9. 기술 운영·모니터링

### Supabase canonical baseline 및 migration 배포 계약

- 새 환경은 저장소의 `supabase/schema.sql`을 공식 canonical baseline으로 먼저 bootstrap한 뒤 `supabase/migrations`를 파일명 순서대로 적용한다. migration-only fresh chain이나 Dashboard SQL dump 수동 실행을 bootstrap 대안으로 사용하지 않는다.
- 기존 환경은 Supabase migration 상태와 마지막 적용 버전을 확인한 뒤 아직 적용되지 않은 새 migration만 순서대로 적용한다.
- 원격 적용 전 preflight에서 `public.profiles`와 `profiles.id`, `profiles.nickname`, `profiles.public_code`, `profiles.title`, `public.generate_profile_public_code(uuid)`의 존재를 확인한다. 하나라도 없으면 baseline drift로 판정하고 적용을 중단한다.
- 적용 후 `public.get_public_crew_profile(text)`의 revoke/grant 상태를 확인하고, anon/authenticated 역할 smoke test로 anon 실행 거부와 authenticated 정상 조회를 각각 검증한다.

### 매일 확인할 신호

- Production 홈과 핵심 route HTTP 상태
- `/api/home-feed`의 `sourceStatus`, `syncedAt`, 자료 수
- `/api/media`의 cache 상태, 기사 이미지 접근성
- 자동수집 마지막 성공 시각, 신규·중복·반려 수
- Vercel function 오류와 응답 시간
- GitHub cache refresh 최근 실행 상태
- Supabase auth/API 오류와 비정상 쓰기

### 목표 기준

- Production 가용성: 월 99.5% 이상
- 자동작업 성공률: 월 98% 이상
- 미디어 중복 공개: 0건
- 설명 URL 혼입: 0건
- 잘못된 공개 범위·비공개 정보 노출: 0건
- P1 콘텐츠 오류 정정: 확인 후 24시간 이내
- 일반 커뮤니티 신고 1차 응답: 2영업일 이내
- stale fallback 사용률: 측정 후 1% 미만 목표

### 비용 통제

- 데이터가 없을 때 LLM·검색·캐시 갱신을 반복하지 않는다.
- 고정 15분 갱신을 사용하지 않고 신규 등록 이벤트에만 공개 캐시를 갱신한다.
- Home에는 최신 실제 미디어 최대 2개만 노출하고 embed·autoplay를 사용하지 않는다.
- Home 최근 탐사 신호는 public projection의 최신 4개만 가져와 4열→2열→1열 반응형 grid로 제공한다. 카드 전체는 공개 상세 링크이며, 공개 철회·수정·삭제의 cache invalidation 이후 stale 신호를 유지하지 않는다.
- 새 외부 SaaS는 기존 Admin·Notion·Supabase로 해결할 수 없는 운영 문제와 월 비용 상한이 명확할 때만 도입한다.
- 월 1회 Vercel·Supabase·API 사용량을 확인하고 무료/저비용 범위를 초과하기 전에 조정한다.

## 11. 백업과 복구

현재 저장소에는 전체 백업·복원 성공을 증명하는 운영 기록이 없다. 다음을 운영 필수 작업으로 추가한다.

- Supabase: 제공되는 자동 백업 정책 확인, 월간 논리 백업, 분기 복원 훈련
- Notion: 주간 핵심 DB 구조·페이지 ID·공개 필드 JSON 스냅샷, 월간 export
- 사본: 최소 2개 저장매체에 두고 하나는 운영 계정과 분리
- 무결성: 월 1회 export 열기, 레코드 수·첨부·체크섬 확인
- 한계: Notion export는 작업공간을 즉시 원상복구하는 백업이 아니므로 구조화 스냅샷과 복원 절차를 별도로 유지
- 복구 목표: 공개 사이트 RTO 8시간 이내, 승인 콘텐츠 RPO 24시간 이내
- GitHub: `main` 보호, release tag 또는 검증된 Production 커밋 기록
- Vercel: 이전 정상 Production deployment ID와 custom-domain alias 기록
- 비밀: 값은 백업 문서에 기록하지 않고 비밀 저장소의 존재·회전일·소유자만 기록

복구 우선순위:

1. 인증·개인정보 경계
2. 공개 게시물 정본
3. 사용자 기록
4. 이미지·캐시 등 재생성 가능한 파생 데이터

| P2 | stale fallback이 HIT/MISS와 독립 상태로 충분히 관측되지 않음 | `STALE` 상태와 소스별 오류율 계측 |
| P2 | 미디어 자동등록은 즉시 공개 예외라 오분류 위험이 있음 | 다음 운영일 전수/표본 감사와 긴급 보관 절차 유지 |
| P2 | Notion·Supabase·Admin에 상태가 분산됨 | 읽기 전용 운영 현황판으로 통합하되 정본은 이동하지 않음 |
| P2 | 전체 콘텐츠 캘린더가 없음 | 기존 도구 하나에 최소 필드 캘린더 생성 |
| P2 | wildcard 404·경로별 SEO·일부 E2E skip이 남음 | 제품 로드맵 Phase 0에서 처리 |

## 14. 90일 실행안

### 0~14일 — 운영 기준선

- 이 문서를 승인하고 담당자·승인권을 확정한다.
- 한 곳에 최소 콘텐츠 캘린더를 만든다.
- 일간/주간 체크리스트와 정정 기록 양식을 만든다.
- 자동작업 마지막 성공·신규·중복·오류를 한 화면 또는 보고서로 모은다.
- 커뮤니티 신고 접수 임시 경로와 긴급 숨김 담당자를 공개한다.
- Supabase·Notion 백업 가능 범위와 복구 담당자를 확인한다.

통과 기준: 담당자 미지정 작업 0개, Production 승인 없는 배포 0개, 자동작업 상태 확인 가능.

### 15~45일 — 안전한 관리 도구

- Admin에 DRAFT 연령, 검수 대기, 자동수집 출처·권리 상태를 보여준다.
- 커뮤니티 신고·숨김·처리 이력의 최소 기능을 구현한다.
- `STALE`과 소스별 실패율·마지막 성공 시각을 기록한다.
- Notion 미디어 품질 검사를 정기 실행한다.
- 월간 논리 백업과 첫 복원 표본 테스트를 수행한다.

통과 기준: P1 운영 공백 0개, 신고 처리 이력 100%, 복원 표본 성공.

### 46~90일 — 측정과 조정

- 첫 월간 운영 보고서를 발행한다.
- 콘텐츠 유형별 실제 소요 시간과 반려율로 발행량을 조정한다.
- 자동등록 오분류율이 높으면 즉시등록 범위를 축소하거나 검수함으로 전환한다.
- 사용하지 않는 자동화와 중복 데이터 경로를 제거한다.
- 제품 로드맵과 운영계획을 함께 갱신한다.

통과 기준: 자동작업 성공률 98% 이상, 중복 공개 0, 비공개 정보 노출 0, 정정 SLA 준수.

## 15. 운영 의사결정 규칙

- 정확성·개인정보·권리와 일정이 충돌하면 일정을 미룬다.
- 자동화와 사람이 충돌하면 공개 상태는 사람의 마지막 명시적 결정이 우선한다.
- 데이터가 0건이면 0건을 정상 상태로 보여주며 가짜 자료를 채우지 않는다.
- 한 기능이 운영 책임자를 요구하지만 담당자가 없으면 기능을 공개하지 않는다.
- 공개 후 관리 비용이 월간 운영 용량을 넘으면 새 기능보다 기존 범위 축소를 우선한다.
- 중요한 IA·데이터 계약·공개 범위·자동화 변경은 이 문서와 `product-roadmap.md`를 함께 갱신한다.
